## ② 截图方案：实测取证与定案

这是本轮的主体，也是**唯一一处必须先取证再写代码**的决策。三条路都实测过：

| 方案 | 实测结果 | 结论 |
|---|---|---|
| `pywinauto.capture_as_image()` | 探针实测第一个截到的窗口就是我们的**「捕获确认」对话框**——走屏幕 `BitBlt`，天然被遮挡物挡住 | 对桌面腿可用（要的就是「用户眼前那块屏幕」），对浏览器腿是错的 |
| `PrintWindow(hwnd, dc, PW_RENDERFULLCONTENT)` | WorkBuddy 亚克力窗口、msedge 都穿透遮挡成功，**但msedge 抓到内容水平重复三次**（窗口 rect `(-8,-1088)-(1928,-32)`，跨屏负坐标，同一页面并排 3 份） | ✗ 弃用 |
| `PIL.ImageGrab.grab(bbox=窗口绝对矩形, all_screens=True)` | 内容正确、**无重复**（左右半图平均差 **45.23**；重复时会趋近 0），多显示器负坐标正常 | ✅ **定案** |

**PrintWindow 的三倍重复是不是 Chromium 通用缺陷？** 隔离实验否掉了：自建 tkinter 窗口在
**完全相同的正/负坐标条件下** PrintWindow 正常（红色定位标记恰好出现 1 次）⇒ 是
**Chromium 合成器 + 多显示器**的特有问题。

维护者随后给出关键线索：「我试了影刀web 应该是走的桌面截图，因为他的 web 元素截图会把
浏览器**前面窗口的内容也截取到**，应该是根据坐标来的。你看下水平重复三次这个问题能否解决，
**最好是统一桌面截图了**」——而 ImageGrab 实测恰好复现了这个特征：截图里小红书窗口盖住了
浏览器一部分。⇒ **这不是缺陷，是影刀的实现口径**，统一到坐标截屏同时达成「统一」与
「消掉重复」两个目标。

> 途中踩过的坑一并备查：`PrintWindow` 抓的图是**条纹**（红绿块位置对但整体错行），
> 因为 `Image.frombuffer(..., "raw", "BGR", 0, 1)` 让 Pillow 自行推导 stride。正确做法是
> `GetDIBits` + `biHeight` 取负（top-down）+ 显式 `stride=width*4` +
> `Image.frombuffer("RGBA", (w,h), raw, "raw", "BGRA", w*4, 1)`；判据用已知面积色块占比
> 验证：`BGRA_topdown` red=**0.2273** 精确命中期望 0.227。最终方案改走 ImageGrab，
> 此问题不再存在。

### 架构定案

**扩展侧职责收缩到极限**：截图从扩展移到 host 后，扩展**不再拍图、不再回传 `dataUrl`**
（几百 KB base64 不该穿回传通道），只回 `windowHandle` + content 算好的 `rect`/`viewport`。
MV3 的 `chrome.windows.get(windowId)` 在 Windows 上直接给 Chrome 顶层 hwnd；拿不到回`null`。

**两条腿的红框换算完全不同**（分别做成纯函数）：

- **桌面腿**：`info.rectangle()` 本身就是**绝对屏幕坐标**，与坐标截屏的图**同源** ⇒
  图内像素 = 屏幕坐标 − 窗口原点，**1:1，无 scale / scroll / dpr**。实测窗口 rect
  `(-8,-1088)-(1928,-32)`（负坐标多屏）减法照样成立。
- **浏览器腿**：图内 = `rect_CSS × scale + (视口屏幕原点 − 窗口原点) × scale`，
  其中 `scale = 图宽 / viewport.width`（**不用 `devicePixelRatio` 猜**——Windows 分数缩放下
  可能差 1px，1px 偏在小元素上就是「框没套住」）。
  视口偏移**host 侧推不出来**（`client_rect()` 只是窗口内相对坐标，恒为 `(0,0,w,h)`；
  标签栏/地址栏高度由 Chromium 自己布局）⇒ 必须扩展回传 `window.screenX/screenY`。

### 修掉的真 bug：钳位只钉位置不收窄宽高

判据 `test_browser_box_clamps_partially_scrolled_out` 抓到：元素 `left=-50, width=100`
（横跨 -50~50）时，钳位后正确框宽应为 50，但代码只把 `x` 钉到 0 而不动 `width`，框从 0
铺到 100——**比元素宽一倍，看着像框住了旁边的东西**。修法是「把被切掉的那截从宽高里扣掉」：
`w - (clamped_x - raw_x)`。**同源bug 在 `screen_shot.browser_box_in_window` 与
`verify.preview_box_in_image`（M47.11 遗留，已标 deprecated）两处都有**，本轮一并修，
并都补了「完全在外返回 None」。

## 收尾时抓到的事故：探针自己把工作区搞脏了（并连带一个「红得像实现坏了」的假象）

上一节三个实例之外，本轮收尾复跑负向探针时**基线直接红**在
`screen_shot.py:205ZeroDivisionError`。按「对照跑红了先查基线是不是脏的」取证，
结论是**基线确实脏**，而且脏法有四层，每层都由探针自己的缺陷造成：

1. **`SENTINEL` 只被检查、从不写入**（`assert_no_sentinel()` 恒绿）。原先
   `write_bytes(text.replace(old, new, 1))` 注入时不带任何标记，于是「上一轮 run 被
   中断在 `finally` 之前」留下的注入**根本检不出来**。记忆里早有「还原自愈必须唯一凭证
   （哨兵），否则陈旧备份覆盖新改动」这条，这次是它的反面：**没有凭证 ⇒ 中断留痕无法发现**。
2. **`originals` 快照 + BASELINE 检查都在 `try` 之外**：两个 `return 2` 直接跳过
   `finally` 的还原 ⇒ 一旦基线红，脏态被**永久固化**。
3. **修好 1、2 之后，第一版哨兵拼接又是错的**（前后栽了三次，逐条记在
   `inject_payload()` 的 docstring 里）：
   - 哨兵与原文下一行**同行** ⇒ 那行代码被注释掉。人工还原时极易连带丢掉，
     **实测 C1b 的 `self._desktop_tab_host = self` 就是这么差点丢的**。
   - 分支依据写成 `new.endswith("\n")`，应为 **`old`**（判断"原文被吃掉多少换行"）。
     写反时 11 处全粘行、写对时 13 处全过——**这类错误不会有编译错误，只会静默粘行**。
   - 后缀判定写成 `target.suffix == ".mjs"`，而受管的扩展文件是 **`.js`** ⇒ 会走进
     `# ` 分支；`#` 在 JS 里是**语法错误**（与记忆中「JS 哨兵取 `//`」那条一致）。
4. **我的还原脚本本身也写错**：按 `MARK.split(":")[1]` 反解，把哨兵的**标签**
   （`A6`/`C1b`）当成代码插回文件，留下 `A6`、`C1b        self._desktop_tab_host = self`
   这种垃圾行——`ruff` 立刻报 26 个语法错。**正确做法是删掉哨兵整行、把 `new` 反向替换回
   `old`，不做任何"反解"**。

处置与沉淀：

- 四处残留（A6/B2/B3/C1b）按「删哨兵行 + `new`→`old`」逐条还原，**再由判据证明**：
  `ruff` 全绿 + 受影响四个文件 **186 passed / 0 FAILED**（不靠"看起来对"）。
- 哨兵拼接抽成**共用函数** `inject_payload()`，探针与验证脚本走同一份逻辑——否则会
  出现"验证的和跑的不是一回事"。另用 `ast.parse` / `node --check` 对**整文件**验证，
  并断言「删掉哨兵行后逐字闭合」；此处也栽了一次：验证器先截代码中段当片段解析，
  13 处全报"语法错"——那是**验证器不合格**（片段不是完整语法单元、`await` 在非 async
  上下文、中文注释被切半），不是注入有问题。**验证工具本身出错时要先怀疑验证工具。**

## 真机反馈：「预览中没有截图」⇒根因是扩展跑的是旧快照（不是代码错）

维护者报「预览中没有截图」。**先看 trace再下结论**（`%TEMP%\rpa-capture-trace.log`）：

```
"arm_acked",  "build": "0.6.3", "expected": "0.8.0", "stale": true
"arm_stale",  "build": "0.6.3", "expected": "0.8.0"
"shot", "has_hwnd": false, "hwnd": null, "has_rect": true, "has_viewport": true
```

`has_rect`/`has_viewport` 都在（M47.11 的老字段正常），**唯独 `windowHandle` 是 null**
——因为浏览器里跑的是 **0.6.3** 版扩展，它不认识本轮才加的 `windowHandle`。
**`Load unpacked` 载入即快照**：改 `extension/` 的代码不去 `chrome://extensions` 点刷新，
浏览器里永远跑旧的。这条记忆里早就有（「修复无效」事故根因），本轮是它第一次
**以「新字段读不到」的形式**出现——红框、校验、老功能全都正常，只有新功能沉默失效。

顺带暴露一个真缺口：`arm_stale` 此前**只落 trace、GUI 上没有任何提示**（记忆里
「arm_stale GUI 提示」这条欠账），所以现场只能靠猜。修法三段：

1. `ExtensionCaptureSession.build_mismatch` 属性（arm ack 时记下实际/期望版本）。
2. `verify._exchange` **透传 `extBuild`**——background 一直在回这个字段，此前被丢掉了。
   有了它host 侧才可能判版本，而不是靠症状猜。
3. 新增纯函数 `verify.shot_failure_reason()` 把失败分成**三类**（原先两类）：
   - `ext-stale` —— 跑的是旧快照 ⇒ **去 chrome://extensions 点刷新**；
   - `no-window-handle` —— 扩展是新的但没拿到窗口句柄 ⇒ 切到该浏览器窗口；
   - `shot-failed` —— 句柄有但截屏失败 ⇒ 换个窗口状态。

   GUI 文案相应分档，`ext-stale` 直接把版本号和 `chrome://extensions` 写出来。

**为什么必须把 `ext-stale` 单列一档**：它的现场症状是「校验正常、红框正常、就是没图」，
按旧口径报「未能定位到浏览器窗口」会让用户去切窗口——切一百次也没用，
而真实处置只是点一下刷新。**处置不同的失败原因不能共用一句文案。**

判据分三段各钉一层（负向验证 N1/N2/N3 各红**恰好 1 条**，无冗余也无漏网）：

| 层 | 判据 | 注入 |
| --- | --- | --- |
| 透传 | `test_verify_result_carries_extension_build` | N1 删 `extBuild` 透传 |
| 分类 | `test_shot_failure_reason_names_extension_stale_first` | N2 退回旧口径 |
| 链路 | `test_browser_preview_passes_stale_reason_through_to_gui` | N3 `_browser_preview` 丢 `ext-stale` 档 |

**链路那层原先无人钉**：纯函数钉「怎么分类」、GUI 判据钉「拿到 ext-stale 怎么写文案」，
中间这步（旧扩展 → 旧文案链）两边都够不着——而真机现场正是这里让人无从判断。
**「两段各自绿的判据」不等于「链路通」**，同M50 的path-pruning 那条教训。
