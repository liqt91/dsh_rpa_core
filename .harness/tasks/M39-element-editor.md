# M39 元素捕获之后的体验：校验口径 / 数据展示 / 元素编辑器

状态：`active`

由来：维护者 2026-09-23 要求「看下元素捕获的整个链路，影刀是怎么做的，对比并从用户体验
角度评估」，随后拍板「按 ① ② ③ 顺序推进」。影刀对标材料的来源：联网查证（官方文档）
+ 本地已抓取的影刀命令文档（`docs/yingdao-cmds/`、`docs/yingdao-cmds-desktop/`）。

## 0. 一句话结论

我们的捕获链路骨架与影刀**同构**（捕获入口 → 高亮 → 手势确认 → 描述符 → 落库），差距
全部集中在**「捕获之后那一步」**：影刀给出的是**元素编辑器**（DOM 节点树 + 属性勾选 +
活体校验的迭代回路），我们给的是一行 `selector` 文本框加一个只读 metadata 块。

## 1. 链路对比（实测 + 查证）

| 环节 | 影刀 | rpa_core |
|---|---|---|
| 高亮 | 蓝框 | 红框 `#ff3b30`（网页 / 桌面同色） |
| 拾取手势 | Ctrl+左键 | Ctrl+左键 / 右键 / 桌面 F9，Esc 取消 |
| 通道选择 | **用户选**（新元素 / 深度模式 / CV 智能） | **自动**（双通道竞速，先回传者胜） |
| 捕获后 | **元素编辑器** | **确认框**（改名 + 单行 selector + 只读 metadata） |
| 定位表达 | 节点树勾选 + 属性勾选 + XPath + 通配符 | 手写 CSS / 手写 locator JSON |
| 校验 | **活体**（页面高亮闪烁 + 命中数） | **结构**（不查页面） |
| 修复 | 手动「修复元素」（AI 生成更稳属性） | 设计期无入口（运行期**自动**候选回退） |
| 相似元素 / 锚点 | ✅ / ✅ | ✗ / ✗ |

**我们领先的地方**（不因本轮改动而变，且是别丢的强项）：

1. 运行期**自动**自愈候选回退，影刀要人发现坏了再点「修复元素」；
   且「主选择器命中但预检不过 → 不重试」这条取舍比影刀更保守（换候选＝换一个元素点，
   比失败更危险）。
2. 执行前预检的**三级错误码**分开报（`ELEMENT_COVERED` / `ELEMENT_DISABLED` /
   `ELEMENT_NOT_VISIBLE`），不是笼统的「未找到控件」。
3. **混合单入口**：用户不用先判断目标是网页还是桌面。
4. 多手势（右键 = mac 触控板双指点按，是真需求）。

## 2. 本里程碑三件事（按性价比排序）

### 2.1 ① 校验口径对齐 Web 侧（已完成）

**差距**：GUI 元素库的「校验」按钮走 `_verify_element` → `selector_errors()`，只判
「css 非空 / locator 是合法 JSON」，**根本不连页面**；但状态栏说的是「元素 X 校验通过」。
**Web 侧同一能力已经澄清过**（按钮 `title="结构校验"`，devserver 返回
`note="结构校验；活体验证（命中数）需在捕获会话内完成"`）——两形态口径不一致，弱的是 GUI。

迁自影刀的用户点「校验」看到「通过」，会以为元素在页面上定位得到。**「以为校验了、
其实没校验」正是本项目最在意的一类静默错误**，所以这里按 §3 决定 1 处理。

落点：`gui/element_panel.py`（按钮文案 `校验` → `结构校验` + tooltip）、
`gui/app.py::_verify_element`（状态栏消息自带限定语）。判据钉在新文案的**限定语**上，
不只是「包含校验通过」。

### 2.2 ② 展示「已捕获但从未展示」的数据（已完成）

`content.js::buildDescriptor` 一直回传 `selector.candidates`（含每条**实测** `matchedCount`）
与语义特征（`role` / `accessibleName` / `placeholder` / `label` / `containerText`）和页面指纹
（`url` / `title`）；`ElementDescriptor` 也一直把它们落盘。但 `ElementDialog` 只显示
`tag/id/classes/text/rect`——**保住数据做到了，暴露数据没做**。结果是用户不知道自愈能力
存在，也无从据 `accessibleName` / `label`（消歧最有用的两项）在命中多个时人工判断。

落点：`gui/element_panel.py` 的 `semantic_meta_text` / `candidates_text`（**只读**、可选中
复制）。`matchedCount > 1` 的候选如实标「不唯一」，而不是替用户过滤掉——选择更稳的候选是
用户的判断，不是展示层的判断。

**顺带实测发现（探针 `probe_element_dialog_display.py`）**：真机捕获的桌面描述符
`metadata` 里有 `className`，而确认框**从不显示它**。`className` 正是 win32 侧定位
**无窗口文本控件**（ListBox/ComboBox）的唯一手段，也是 `classNameRe` 的输入——一并补上
`name` / `className`。

**刻意不展示** `windowHandle` / `point`：它们是本次会话的运行期值（句柄每次启动都变），
摆出来会诱导用户粘进 locator，写出一个下次必定失效的元素。

### 2.3 ③ 元素编辑器（v1 已完成；v2 待拍板，见 §5）

影刀编辑器的重心是「在**活页面**上勾出一套属性」。我们离线时做不了节点树与活体校验，
但用户真正卡住的那一步不需要活页面：

> **不写 CSS、不写 JSON，也能选出一个定位方案。**

**v1（离线，本轮落地）** `gui/element_editor.py`：

1. **候选可选** —— 捕获时的备选定位（带实测命中数）点一下即成为主定位；
2. **桌面 locator 字段化** —— 勾选框代替手写 JSON，字段集**按 backend 分**（见 §3 决定 2）；
3. **就地结构校验** —— 每次改动都拿**模型**判一次，错误显示在对话框内，不弹窗、不拦在
   状态栏（那是确认框的做法，编辑器需要「改 → 校验 → 再改」的回路）。

入口：元素库「编辑」按钮 + 列表**双击**（影刀元素库就是双击开编辑器，用户有这个肌肉记忆）。

## 3. 关键设计决定

| # | 决定 | 理由（含被否掉的选项） |
|---|---|---|
| 1 | ① 只改文案，**不改校验语义** | 让 `selector_errors` 去连页面是不可能的（离线元素库没有页面）。零风险的下限是「说清它查了什么」，与 Web 侧对齐 |
| 2 | 编辑器字段集**按 backend 分** | 实测两执行器消费的 locator 字段**完全不重叠**（§3.1）。提供对面后端的字段＝在 UI 上生产「写了没人读」的静默死字段 |
| 3 | 只有**实测过命中数**的候选可提升 | 提升要把候选的实测值写成新 `verifyCount`；没有实测值就只能猜，而 `verifyCount` 的语义就是「这个是实测的」。宁可不给按钮，也不给一个假的数 |
| 4 | 提升是**交换**不是覆盖 | 旧主定位按序放回候选队首（它的实测命中数就是 `verifyCount`，是实测值不是估计值），所以一条备选都不丢、也不是单向操作 |
| 5 | 判据权威是**模型**，界面不另立规则 | 界面只做两件事：把模型报错**译成人话**、把「不该出现的状态」提前拦住。两套规则必然漂移，而漂移的后果是「界面放行、执行器拒绝」 |
| 6 | 死字段**提示**而非静默移除 | locator 里的 `menuPath` / 对面后端字段执行器读不到；保存会去掉它们，但必须**说出来**。静默改用户文件是另一类静默错误 |
| 7 | 编辑器**不改元素名** | 元素名是身份。改名走捕获/入库那条已有的「同名覆盖保护」路径，再开一条会多出一份语义要同步 |

### 3.1 字段集按 backend 分的实测依据

`grep -o 'locator\.[a-z_]*'` 逐点核过两个执行器的读取面：

| locator 字段 | uia `desktop.py::_find` | win32 `desktop_win32.py::_find` |
|---|---|---|
| `controlType` | ✅ | ✗ |
| `automationId` | ✅ | ✗ |
| `name` | ✅（映射成 `title=`) | ✗ |
| `title` | ✗ | ✅ |
| `className` | ✗ | ✅ |
| `classNameRe` | ✗ | ✅ |
| `controlId` | ✗ | ✅ |
| `foundIndex` | ✗ | ✅ |
| `menuPath` | ✗ | ✗ |
| `handle` | ✗ | ✗ |

这条事实由测试 `test_field_tables_match_what_executors_actually_read` **自维护**：用 `ast`
扫执行器里全部 `locator.<字段>` 读取点，折回别名与界面字段表逐一比对。任一边变了就红，
不需要有人记得同步两份清单。**它在本轮就真的拦下了一次注入**（往 uia 表里塞 `menuPath`）。

**实测发现的新缺口（已登记 BACKLOG）**：`menuPath` 在 locator 里**没有任何执行器读它**
（只作为 `desktop_win32.menuSelect` 的**命令输入**被读），而 `DesktopLocator` 的 win32
身份字段清单**把 `menuPath` 算作合法身份** —— 也就是说可以写出一个「模型通过、执行器
永远找不到」的 locator。这属于「声明与实现不一致」，与 M38 查处的那批同类。

## 5. ③-2 待决策（需要维护者拍板）

### 5.1 活体校验：能力已存在，缺的是通道

内容脚本的**动作路径里本来就有**活体校验所需的一切：`document.querySelectorAll(selector).length`
与遮挡 / 可见性预检（`ELEMENT_NOT_VISIBLE` / `ELEMENT_COVERED`）。所以 ③-2 **不是**写查询代码。

缺的是通道：GUI 的 `_capture_element` 在 `work()` 的 `finally` 里就 `session.close()`
（`_disarm()` 下发 `capture_disarm` 并关闭全部 bridge 通道），而对话框是在那**之后**
才弹出的（`_on_element_captured` → `_confirm_element_save`）。即：用户看到对话框时，
捕获会话已经撤防关掉了。

三个选项：

- **A. 捕获期活体校验**：把会话生命周期延到对话框关闭后（`pick` 拿到结果只 disarm、
  不 close）。收益最大（用户就在那个界面里改定位），代价是会话 / 通道生命周期与取消语义
  要重新设计，且有「对话框长开 → 通道一直挂着」的泄漏面。
- **B. 元素库里的「用当前浏览器的页面校验」**：走一条独立的扩展命令通道（不依赖捕获会话）。
  没有生命周期问题，但要有「用哪个标签页」的选择语义，且桌面元素仍然做不到。
- **C. 不做**：保持结构校验（即 ① 的口径）。成本为零，收益是「用户永远不能在改完看一眼
  命中数」。

**建议 A，但把范围限在「捕获确认框内」**（不做常驻编辑器），并且先只做
「改选择器 → 打一次命中数」，不做节点树。理由是：这正是影刀的核心回路，也是本轮 ① 的
限定语「活体验证在捕获时完成」所指的那件事；不兑现它，① 的文案就一直是句空话。

### 5.2 DOM 节点树要不要做

影刀的节点树依赖**活 DOM**（页面上可交互的节点层级）。做它等于要新增一条
「取某元素的祖先 / 兄弟 / 子节点摘要」的扩展 op（`page.outline`），并处理深度上限、
跨 iframe、Shadow DOM、性能。**建议 ③-2 不做**，等 A 落地后按真实用户反馈再定。

### 5.3 另外两件本轮未做、也不建议现在做的

- **相似元素成组**（影刀一键成组 + `循环相似元素`）：这是**新命令能力**，不是编辑器 UI，
  要动 manifest / 执行器 / 契约，另立里程碑。
- **AI 修复元素 / AI 辅助定位**：需要模型调用，超出本项目的 `scope.out`（见
  `project_state.json` 的 `out` 列表里有 MCP / 在线命令生成）。

## 6. 剩余

- ③-2 按 §5.1 的决策推进（当前：**等维护者拍板**）；
- `menuPath` 作为 locator 身份字段的「声明与实现不一致」已进 BACKLOG，跟 ③-2 或独立小任务
  一起修（改动面小：要么让某个执行器消费它，要么把它从 win32 身份清单里去掉）。
- **Web 编辑器未同步本轮改动（显式欠账）**：① 不需要动 Web（Web 侧本来就是澄清过的口径）；
  但 ② 的候选/语义特征展示与 ③ 的元素编辑器**只在 GUI 落地**，`devserver/static` 那侧同源
  的 `metaEl` / `openElementDialog` 还是旧样。两端形态一致是这个项目一直在守的东西
  （M23 切 G 就是「GUI 功能补齐」），所以这笔账要么补上、要么明确接受差异——**不建议
  默默留着**：同一个元素在两端看到的信息不一致，本身就是一类语义错位。
