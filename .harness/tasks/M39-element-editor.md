# M39 元素捕获之后的体验：校验口径 / 数据展示 / 元素编辑器

状态：`done`

由来：维护者 2026-09-23 要求「看下元素捕获的整个链路，影刀是怎么做的，对比并从用户体验
角度评估」，随后拍板「按 ① ② ③ 顺序推进」。影刀对标材料的来源：联网查证（官方文档）
+ 本地已抓取的影刀命令文档（`docs/yingdao-cmds/`、`docs/yingdao-cmds-desktop/`）。

## 0. 一句话结论

我们的捕获链路骨架与影刀**同构**（捕获入口 → 高亮 → 手势确认 → 描述符 → 落库），差距
全部集中在**「捕获之后那一步」**：影刀给出的是**元素编辑器**（DOM 节点树 + 属性勾选 +
活体校验的迭代回路），我们给的是一行 `selector` 文本框加一个只读 metadata 块。

## 1. 链路对比（实测 + 查证）

| 环节 | 影刀 | rpa_core |
|---|---|---|
| 高亮 | 蓝框 | 红框 `#ff3b30`（网页 / 桌面同色） |
| 拾取手势 | Ctrl+左键 | Ctrl+左键 / 右键 / 桌面 F9，Esc 取消 |
| 通道选择 | **用户选**（新元素 / 深度模式 / CV 智能） | **自动**（双通道竞速，先回传者胜） |
| 捕获后 | **元素编辑器** | **确认框**（改名 + 单行 selector + 只读 metadata） |
| 定位表达 | 节点树勾选 + 属性勾选 + XPath + 通配符 | 手写 CSS / 手写 locator JSON |
| 校验 | **活体**（页面高亮闪烁 + 命中数） | **结构**（不查页面） |
| 修复 | 手动「修复元素」（AI 生成更稳属性） | 设计期无入口（运行期**自动**候选回退） |
| 相似元素 / 锚点 | ✅ / ✅ | ✗ / ✗ |

**我们领先的地方**（不因本轮改动而变，且是别丢的强项）：

1. 运行期**自动**自愈候选回退，影刀要人发现坏了再点「修复元素」；
   且「主选择器命中但预检不过 → 不重试」这条取舍比影刀更保守（换候选＝换一个元素点，
   比失败更危险）。
2. 执行前预检的**三级错误码**分开报（`ELEMENT_COVERED` / `ELEMENT_DISABLED` /
   `ELEMENT_NOT_VISIBLE`），不是笼统的「未找到控件」。
3. **混合单入口**：用户不用先判断目标是网页还是桌面。
4. 多手势（右键 = mac 触控板双指点按，是真需求）。

## 2. 本里程碑三件事（按性价比排序）

### 2.1 ① 校验口径对齐 Web 侧（已完成）

**差距**：GUI 元素库的「校验」按钮走 `_verify_element` → `selector_errors()`，只判
「css 非空 / locator 是合法 JSON」，**根本不连页面**；但状态栏说的是「元素 X 校验通过」。
**Web 侧同一能力已经澄清过**（按钮 `title="结构校验"`，devserver 返回
`note="结构校验；活体验证（命中数）需在捕获会话内完成"`）——两形态口径不一致，弱的是 GUI。

迁自影刀的用户点「校验」看到「通过」，会以为元素在页面上定位得到。**「以为校验了、
其实没校验」正是本项目最在意的一类静默错误**，所以这里按 §3 决定 1 处理。

落点：`gui/element_panel.py`（按钮文案 `校验` → `结构校验` + tooltip）、
`gui/app.py::_verify_element`（状态栏消息自带限定语）。判据钉在新文案的**限定语**上，
不只是「包含校验通过」。

### 2.2 ② 展示「已捕获但从未展示」的数据（已完成）

`content.js::buildDescriptor` 一直回传 `selector.candidates`（含每条**实测** `matchedCount`）
与语义特征（`role` / `accessibleName` / `placeholder` / `label` / `containerText`）和页面指纹
（`url` / `title`）；`ElementDescriptor` 也一直把它们落盘。但 `ElementDialog` 只显示
`tag/id/classes/text/rect`——**保住数据做到了，暴露数据没做**。结果是用户不知道自愈能力
存在，也无从据 `accessibleName` / `label`（消歧最有用的两项）在命中多个时人工判断。

落点：`gui/element_panel.py` 的 `semantic_meta_text` / `candidates_text`（**只读**、可选中
复制）。`matchedCount > 1` 的候选如实标「不唯一」，而不是替用户过滤掉——选择更稳的候选是
用户的判断，不是展示层的判断。

**顺带实测发现（探针 `probe_element_dialog_display.py`）**：真机捕获的桌面描述符
`metadata` 里有 `className`，而确认框**从不显示它**。`className` 正是 win32 侧定位
**无窗口文本控件**（ListBox/ComboBox）的唯一手段，也是 `classNameRe` 的输入——一并补上
`name` / `className`。

**刻意不展示** `windowHandle` / `point`：它们是本次会话的运行期值（句柄每次启动都变），
摆出来会诱导用户粘进 locator，写出一个下次必定失效的元素。

### 2.3 ③ 元素编辑器（v1 已完成；v2 待拍板，见 §5）

影刀编辑器的重心是「在**活页面**上勾出一套属性」。我们离线时做不了节点树与活体校验，
但用户真正卡住的那一步不需要活页面：

> **不写 CSS、不写 JSON，也能选出一个定位方案。**

**v1（离线，本轮落地）** `gui/element_editor.py`：

1. **候选可选** —— 捕获时的备选定位（带实测命中数）点一下即成为主定位；
2. **桌面 locator 字段化** —— 勾选框代替手写 JSON，字段集**按 backend 分**（见 §3 决定 2）；
3. **就地结构校验** —— 每次改动都拿**模型**判一次，错误显示在对话框内，不弹窗、不拦在
   状态栏（那是确认框的做法，编辑器需要「改 → 校验 → 再改」的回路）。

入口：元素库「编辑」按钮 + 列表**双击**（影刀元素库就是双击开编辑器，用户有这个肌肉记忆）。

## 3. 关键设计决定

| # | 决定 | 理由（含被否掉的选项） |
|---|---|---|
| 1 | ① 只改文案，**不改校验语义** | 让 `selector_errors` 去连页面是不可能的（离线元素库没有页面）。零风险的下限是「说清它查了什么」，与 Web 侧对齐 |
| 2 | 编辑器字段集**按 backend 分** | 实测两执行器消费的 locator 字段**完全不重叠**（§3.1）。提供对面后端的字段＝在 UI 上生产「写了没人读」的静默死字段 |
| 3 | 只有**实测过命中数**的候选可提升 | 提升要把候选的实测值写成新 `verifyCount`；没有实测值就只能猜，而 `verifyCount` 的语义就是「这个是实测的」。宁可不给按钮，也不给一个假的数 |
| 4 | 提升是**交换**不是覆盖 | 旧主定位按序放回候选队首（它的实测命中数就是 `verifyCount`，是实测值不是估计值），所以一条备选都不丢、也不是单向操作 |
| 5 | 判据权威是**模型**，界面不另立规则 | 界面只做两件事：把模型报错**译成人话**、把「不该出现的状态」提前拦住。两套规则必然漂移，而漂移的后果是「界面放行、执行器拒绝」 |
| 6 | 死字段**提示**而非静默移除 | locator 里的 `menuPath` / 对面后端字段执行器读不到；保存会去掉它们，但必须**说出来**。静默改用户文件是另一类静默错误 |
| 7 | 编辑器**不改元素名** | 元素名是身份。改名走捕获/入库那条已有的「同名覆盖保护」路径，再开一条会多出一份语义要同步 |

### 3.1 字段集按 backend 分的实测依据

`grep -o 'locator\.[a-z_]*'` 逐点核过两个执行器的读取面：

| locator 字段 | uia `desktop.py::_find` | win32 `desktop_win32.py::_find` |
|---|---|---|
| `controlType` | ✅ | ✗ |
| `automationId` | ✅ | ✗ |
| `name` | ✅（映射成 `title=`) | ✗ |
| `title` | ✗ | ✅ |
| `className` | ✗ | ✅ |
| `classNameRe` | ✗ | ✅ |
| `controlId` | ✗ | ✅ |
| `foundIndex` | ✗ | ✅ |
| `menuPath` | ✗ | ✗ |
| `handle` | ✗ | ✗ |

这条事实由测试 `test_field_tables_match_what_executors_actually_read` **自维护**：用 `ast`
扫执行器里全部 `locator.<字段>` 读取点，折回别名与界面字段表逐一比对。任一边变了就红，
不需要有人记得同步两份清单。**它在本轮就真的拦下了一次注入**（往 uia 表里塞 `menuPath`）。

**实测发现的新缺口（已登记 BACKLOG）**：`menuPath` 在 locator 里**没有任何执行器读它**
（只作为 `desktop_win32.menuSelect` 的**命令输入**被读），而 `DesktopLocator` 的 win32
身份字段清单**把 `menuPath` 算作合法身份** —— 也就是说可以写出一个「模型通过、执行器
永远找不到」的 locator。这属于「声明与实现不一致」，与 M38 查处的那批同类。

## 5. ③-2 待决策（需要维护者拍板）

### 5.1 活体校验：能力已存在，缺的是通道

内容脚本的**动作路径里本来就有**活体校验所需的一切：`document.querySelectorAll(selector).length`
与遮挡 / 可见性预检（`ELEMENT_NOT_VISIBLE` / `ELEMENT_COVERED`）。所以 ③-2 **不是**写查询代码。

缺的是通道：GUI 的 `_capture_element` 在 `work()` 的 `finally` 里就 `session.close()`
（`_disarm()` 下发 `capture_disarm` 并关闭全部 bridge 通道），而对话框是在那**之后**
才弹出的（`_on_element_captured` → `_confirm_element_save`）。即：用户看到对话框时，
捕获会话已经撤防关掉了。

三个选项：

- **A. 捕获期活体校验**：把会话生命周期延到对话框关闭后（`pick` 拿到结果只 disarm、
  不 close）。收益最大（用户就在那个界面里改定位），代价是会话 / 通道生命周期与取消语义
  要重新设计，且有「对话框长开 → 通道一直挂着」的泄漏面。
- **B. 元素库里的「用当前浏览器的页面校验」**：走一条独立的扩展命令通道（不依赖捕获会话）。
  没有生命周期问题，但要有「用哪个标签页」的选择语义，且桌面元素仍然做不到。
- **C. 不做**：保持结构校验（即 ① 的口径）。成本为零，收益是「用户永远不能在改完看一眼
  命中数」。

**建议 A，但把范围限在「捕获确认框内」**（不做常驻编辑器），并且先只做
「改选择器 → 打一次命中数」，不做节点树。理由是：这正是影刀的核心回路，也是本轮 ① 的
限定语「活体验证在捕获时完成」所指的那件事；不兑现它，① 的文案就一直是句空话。

### 5.2 DOM 节点树要不要做

影刀的节点树依赖**活 DOM**（页面上可交互的节点层级）。做它等于要新增一条
「取某元素的祖先 / 兄弟 / 子节点摘要」的扩展 op（`page.outline`），并处理深度上限、
跨 iframe、Shadow DOM、性能。**建议 ③-2 不做**，等 A 落地后按真实用户反馈再定。

### 5.3 另外两件本轮未做、也不建议现在做的

- **相似元素成组**（影刀一键成组 + `循环相似元素`）：这是**新命令能力**，不是编辑器 UI，
  要动 manifest / 执行器 / 契约，另立里程碑。
- **AI 修复元素 / AI 辅助定位**：需要模型调用，超出本项目的 `scope.out`（见
  `project_state.json` 的 `out` 列表里有 MCP / 在线命令生成）。

## 7. Web 侧同步 ②（2026-09-23 收尾）

**为什么算欠账而不是差异**：同一个元素在两个编辑器里显示不同的事实，用户会以为「这边没有这条
= 库里没有」。截图类差异可以接受，**数据面的差异不行**——这正是 §1 调研里记的那类静默错位。

**改动**（`src/rpa_core/devserver/static/app.js`）：

- 新增锚点区 `// [element-display-helpers:start] … :end`：`clipElementText` /
  `elementMetadataLines` / `elementSemanticLines` / `elementCandidateLines` /
  `elementDisplayText`，与 GUI `element_panel.py` 的同名三个函数**逐条同口径**。
- `openElementDialog` 的只读区块从**内联拼装**改成
  `metaEl.textContent = elementDisplayText(descriptor)`。内联拼装正是漂移的成因——Web 那份
  漏掉了候选与语义特征。桌面 metadata 同时补 `name` / `className`（`className` 是 win32 侧
  定位无窗口文本控件的唯一手段、也是 `classNameRe` 的输入）。

**验证**（三条判据，各司其职，互不替代）：

1. **node 门禁** `scripts/check_element_display_helpers.mjs`（已进 `check_all.py` 的
   `PURE_FUNCTION_SCRIPTS`，与其余 7 个前端纯函数门禁同一批）：按锚点切片求值，**23 条断言**
   用真实捕获载荷验「渲染出哪几行」——browser 全量行序、候选不唯一标记、`matchedCount` 缺席
   →「命中未实测」、超长值截断 80 + 省略号、坏形状不崩、`windowHandle`/`point` 不出现。
   *这一段只在浏览器里跑*：Python 读源码只能证明「写了这行字」，证明不了「渲染出哪几行」。
2. **契约测试** `tests/contract/test_editor_element_display.py`（4 条）管 Python 测得到的：
   **接线**（确认框真的调用纯函数；回归断言「不能再出现内联拼装」——纯函数没接上去就是死代码）
   与**两端字段口径**（17 个标签集合相等 + 6 个 must-have，后者防「两端一起删」）。
3. **负向验证 4 处注入，两个方向都做**：
   - 摘掉 JS 的候选行 → node 门禁**精确红**，Python 判据仍绿（说明两条判据分工清楚、没有互相顶替）；
   - JS 退回内联拼装 → 接线判据红；
   - JS 少 `className` → 口径判据红 `仅 GUI ['className']`；
   - **GUI 少 `className`（反方向）** → 口径判据红 `仅 Web ['className']`。
   全部逐字节还原并核 md5（`c75d57c22e027d323864c58375ea6bd5` / `7bc5e815a83793f97b4d66aeb22af704`），
   全仓 `grep INJECTED` 无残留。

**结果**：全量 **1159 passed / 21 skipped / 2 xfailed**；**FULL GATE PASSED**（exit 0）。

### 8.4 本轮新发现的四条

#### ① 保存界面本身缺三件事（结构级 + 交互级）

1. **逼用户看 desktop locator JSON**：确认框那一行对桌面元素是
   `{"backend": "win32", "title": "记事本", "controlId": 3}`。字段勾选这件「不用写 JSON」的能力
   **我们已经有了**（`element_editor.py` 的 `LOCATOR_FIELDS_BY_BACKEND`），但被放在**保存之后**的
   另一个窗口里。用户第一眼撞到的仍是一行 JSON，而 `accept()` 对它的容错只有「是不是合法 JSON 对象」。
2. **没有「重新捕获」**：影刀在同一个界面里能「重捕 / 修复」；我们要退回去整条链路重来。
3. **没有相对定位 / 锚点**：这是能力缺口，但与「保存界面」同屏展示，一并登记。

改动面：把 `ElementEditorDialog` 的字段表**复用**进 `ElementDialog`（同一份
`LOCATOR_FIELDS_BY_BACKEND` + 同一个 `locator_problems` 校验），加一个「重新捕获」回调；
相对定位是模型层的新字段，另议。

#### ② 元素资产与指令参数：**值拷贝 + 按 css 反查**（语义级，本轮实测）

`app.py::_insert_element` 把值写进节点（`holder.args[key] = value`），节点里**不存元素名**；
资产的运行期作用只有一处：`browser.py::_element_candidates` 按**归一化的 css 字符串**建索引，
用节点里的 selector 反查候选。于是**在元素库里改一次主定位**会出现下面这个实测结果：

    资产 css=#q（与节点一致）      节点 selector='#q'  -> 候选 2 条
    在元素库里把主定位改成 #q2     节点 selector='#q'  -> 候选 0 条   ← 主定位不变（值拷贝）
                                   节点 selector='#q2' -> 候选 2 条      ← 且自愈候选也没了

即：**改主 css 对已插入指令是「悄悄变差」而不是「没影响」**——主定位不会跟着变（用户以为会），
自愈候选同时失效（用户完全看不到）。这条与影刀的引用模型正好相反，而界面上**没有任何提示**，
迁来的用户必然按影刀肌肉记忆理解。实测脚本：`Path.mkdtemp()` 造流程目录 + `object.__new__`
构造执行器（避开构造函数通道副作用）后调 `_element_candidates`。

需要产品决策（三选一）：① UI 明说「元素库是捕获档案，改它不会更新已插入的指令」；
② 改索引键换成元素名（则节点必须存引用，动流程 schema）；③ 改主 css 时同步更新引用该 css 的节点。
**本轮只登记，不擅自选。**

#### ③ 元素库列表侧与默认名（交互级）

- 无搜索 / 过滤、无多选、无批量结构校验（影刀有批量验证，页面改版后一次筛出坏元素）；
- 默认名两端不一致（GUI `el_{tag}` / Web `{tag}_{时间戳%100000}`），且 desktop 在 Web 侧退化成
  `element_*` —— 与 §7 那类「同一元素两处不同」同源，属**跨端一致性缺陷**。

#### ④ 桌面腿没有元素自愈（能力缺口）

`flow_dir` / `_element_candidates` 只存在于 `executors/browser.py`。所以「元素改版后自愈」这件事
在桌面上**完全不发生**，也没有影刀那样的「修复元素」入口——桌面元素失效只能重新捕获。

### 8.5 我方领先（对标时别丢）

1. **运行期自动自愈**（候选按序回退）：影刀要人先发现坏了、再点「修复元素」；且「主选择器命中但
   预检不过 → 不重试」比影刀更保守（换候选 = 换一个元素点，比失败更危险）。
2. **确认框就显示候选与实测命中数**（含「不唯一」标记）：影刀没有候选概念（一条规则 + 修复）。
3. **只读展示比影刀捕获窗口给得多**：17 个标签含 `role` / `accessibleName` / `label` /
   `containerText` / `url` / `title` / `className`——`accessibleName` / `label` 恰是消歧最有用的两项。
4. **混合单入口**（不用先判断目标是网页还是桌面）；三级错误码分开报；多手势 + Esc 取消。
5. **desktop locator 字段集按 backend 分 + 死字段提示**：影刀 XPath 一把梭，写错就是失效；
   我们把「执行器读不到」这件事在保存前就说出来。

### 8.6 建议排序（性价比）

1. **§8.4-② 先定语义**（零代码，只需一句产品决策）：它现在是个会咬人的静默误解。
2. **§8.4-① 之 1（确认框内嵌字段勾选）**：复用现有字段表与模型校验，不需要新通道，直接消掉
   「让用户看 JSON」。
3. **§5.1 的活体校验（③-2）**：仍是最大体验差，且它是 ①（校验口径文案）兑现的前提。
4. §8.4-① 之 2（重新捕获按钮）+ §8.4-③（列表侧）成本低，可搭车。
5. §8.4-① 之 3 / ④、§5.3 相似元素：能力级，另立里程碑。

### 9.4 一个结构判断：差距有一半在**流程位置**，不在控件数量

影刀把这些控件放在**同一个窗口**里（捕获完立刻可编辑），我方是**两步**：
捕获确认框（`ElementDialog`：名字 / selector 单行 / 只读 metadata / 保存·取消）→ 保存 →
元素库点「编辑」才进 `ElementEditorDialog`。所以「比我们丰富很多」不只是控件多少，
**更是「捕获=编辑」vs「捕获=确认，编辑另开」**。这点决定了：只要还分两步，逐个补控件
的观感收益都会被流程打折。⇒ **P1 应当先修流程位置**。

### 9.5 「Ctrl 未点击时鼠标箭头变蓝」的技术路径（分两侧）

**网页内（推荐先做，低风险）**：`content.js` 已有 `armed` 与 `keydown` 监听（L396 `onKey`）。
在 armed 期间监听 `Control` 的 down/up ⇒ 向 `documentElement` 注入 `cursor: url(<蓝箭头>) x y
!important`，`keyup` / `capture_disarm` / `disarm` 时移除。**完全可逆、无新通道、跨平台**
（浏览器内行为由页面 CSS 决定，不需要 OS 权限）。

**桌面上（真·全局，高风险）**：要改**别的应用窗口之上**的光标，唯一路径是系统级光标替换
（`SetSystemCursor` 换 `OCR_NORMAL`，`SystemParametersInfo(SPI_SETCURSORS)` 恢复），Windows-only。
风险是**恢复**：Ctrl 松开 / 退出 / 异常 / 崩溃四条路径都要还原，否则用户光标**永久变蓝**。
⇒ 建议单独立项、带强恢复设计，且**不要**与网页侧捆在同一片。
**我方有利条件**：桌面 agent **已经在轮询 `GetAsyncKeyState(VK_CONTROL)`**
（`desktop_agent.py` L21 `VK_CONTROL` / L608），触发条件零成本，不需要新钩子。

- **P2（动执行器契约）**：桌面节点树层级 locator（7）＋ 控件级匹配方式（8）。
- **P3（生命周期改造，最重且是多项共用的地基）**：会话保活 → 活体校验（10）＋ 预览（9）＋
