## 〇、战略前提：自研扩展自动化为「一等公民」（维护者决策 2026-09-08）

**决策**：`rpa_core` 的浏览器自动化一律优先走**自研捕获扩展（`extension/`）**——它是一等公民；
`playwright`、`bsk` 降为**二等**（过渡保留，未来可能放弃）。

### 含义与影响

- **命令模型/执行器以自研扩展为主轴设计**：浏览器类命令（launch/navigate/click/input/…）的
  首要执行通道是扩展，而非 Playwright/bsk。
- **能力差距（现状）**：当前 `extension/` **只具备捕获能力**（hover 高亮 + Ctrl+Click 回传描述符），
  **尚无自动化执行协议**。提升为一等公民需扩展执行面：
  - content script 需具备 navigate / click / input / getText / queryAll / waitFor 等执行原语，
    向 background/宿主转发执行结果；
  - 需定义扩展执行协议（命令 → content script 执行 → 结果回传），且与现有 token 配对/回传
    通道（`/api/capture/extension/*`）同构或扩展之；
  - devserver/执行器侧：`browser.*` 命令映射到「扩展执行」，而非 Playwright/bsk。
- **`transport` 参数含义待重估**：现有 `browser.launch` 的 `transport`（`playwright|bsk`）语义
  与影刀的「浏览器类型」不同且已过时；一等公民化后需重定义（或改为「扩展」为主通道，
  playwright/bsk 作为显式回退/升级路线）。
- **不改契约（本期）**：此为设计前提，记录于此；等影刀指令样本齐全（浏览器操作 / 桌面程序），
  再出「会话 vs 对象变量 + 一等公民扩展执行」的整体方案与实践切片。

> 注：本文件为设计调研记录，不涉及契约实现。

## 一、影刀的核心抽象：网页对象变量（无 sessionId 概念）

rpa_core 实测访问影刀「打开网页」文档（`711591442174164992`）确认：

- 「打开网页」指令**返回一个「网页对象」变量**（默认名 `web_page`，可改名、支持 `fx` 引用）。
- 后续「点击元素 / 输入 / 读取」等指令通过「网页对象」下拉选取该变量，**用户零接触底层 id / 引用语法**。
- 即：**会话被包装为流程级具名对象（网页/窗口），随流程自动在指令间传递**，而非暴露 sessionId 句柄。

### 跨指令共同模式（schema 设计依据）

**1. 会话句柄（对象变量）**

| 模式 | 出现频率 | 说明 |
|---|---|---|
| `网页对象`（输入参数） | 39/44 条 | 除「选择浏览器用户」「获取网页对象列表」等少数外，全部接受网页对象作为输入 |
| `保存网页对象至`（输出参数） | 3/44 条 | 仅「打开网页」「获取已打开的网页对象」「选择浏览器用户」产出对象变量 |
| 命名约定 | — | 对象变量名由用户指定（默认 `web_page`），流程内按名称引用，用户零接触底层 id |

→ **结论**：rpa_core 的 `sessionId` 语义与影刀「对象变量」完全等价，需重命名为「网页对象」或保留但编辑器包装为对象下拉（已实现）。

**2. 浏览器类型枚举（显式参数）**

出现在：打开网页、关闭网页、设置Cookie、选择浏览器用户。枚举值：`cef`(影刀浏览器) / `chrome` / `edge` / `ie` / `360se` / `firefox` / `QQBrowser`。均支持 `fx` 变量引用。

→ **结论**：浏览器类型是 rpa_core `transport`（playwright/bsk）的语义超集。一等公民化后，扩展执行通道需能映射此枚举。

**3. 参数类型分布**

| 参数类型 | 频率 | 影刀 UI 表现 | rpa_core 映射 |
|---|---|---|---|
| 文本 + fx（字符串变量） | 约 60% 参数 | 文本输入框，右上角 fx 按钮可切换为变量引用 | `{"type": "string", "fx": true}` |
| 下拉枚举 | 约 20% 参数 | 下拉菜单，固定选项 | `{"type": "enum", "options": [...]}` |
| 数字 | 约 10% 参数 | 数字输入框（秒/像素） | `{"type": "number"}` |
| 布尔 | 约 5% 参数 | 复选框 | `{"type": "boolean"}` |
| 元素选择器 | 约 5% 参数 | 元素库引用 + 捕获按钮 | `{"type": "element_ref"}` |

**4. 错误处理（所有指令通用）**

| 参数 | 说明 |
|---|---|
| `错误处理方式` | 下拉：`继续执行` / `停止` / `重试` |
| `重试次数` | 数字（仅重试时生效） |

→ rpa_core 的 `errorPolicy` 已覆盖此模式。

**5. 等待/延迟（元素操作通用）**

- `等待元素存在(s)`：元素出现/消失的超时时间（秒），出现在几乎全部元素操作指令
- `执行后延迟(s)`：指令执行完成后的等待时间，少数指令有

→ 元素操作指令需统一支持「等待元素超时」参数。

**6. 输入模式（填写类指令共通）**

`填写输入框`、`填写密码框` 均支持：`set_value`（直接设值）/ `模拟人工`（逐字输入）/ `按下键逐字`。后者模拟真实键盘行为，用于触发 JS 事件的页面。

→ rpa_core 的 input 指令需支持此模式枚举。

## 四、与 rpa_core 现状对照（初步）

- 我们：`browser.launch` 输出 `sessionId`；browser.* 引用字段名 `sessionId`，值 `${steps.launch.outputs.sessionId}`；`desktop.attachWindow` 同理。**机制等价于影刀的对象变量引用，但暴露了 sessionId 字段名 + 底层引用语法。**
- 影刀：用户只看「网页对象」变量名；浏览器类型是显式参数。

## 五、已知待决策（44 条指令数据齐全，可推进）

1. **浏览器类型枚举映射**：影刀 7 值枚举（cef/chrome/edge/ie/360se/firefox/QQBrowser）vs rpa_core 现有 `transport`（playwright/bsk）。选项：
   - A：扩展为一等公民后，`transport` 语义改为「通道」（extension/playwright/bsk），浏览器类型作为独立参数
   - B：保留 `transport`，新增 `browserType` 参数，仅 playwright/bsk 通道使用

2. **对象变量命名**：影刀用用户自定义名（默认 `web_page`），rpa_core 用 `${steps.<node>.outputs.sessionId}`。选项：
   - A：编辑器已包装（对象下拉），内部契约不变——**当前实现，无需改动**
   - B：重命名 `sessionId` → `webPage`/`objectRef`（破坏性变更，需迁移）

3. **元素选择器格式**：影刀用「元素库」封装（UI 捕获 + 内部描述符），rpa_core 现有 `elementRef`（CSS selector + 元素描述符）。需确认：
   - 扩展执行通道的元素描述符格式是否与现有 Playwright `ElementHandle` 兼容
   - 元素库是否需要持久化存储（影刀支持「企业云元素库」）

4. **多资源类型**：网页自动化用「网页对象」（sessionId），桌面自动化用「窗口对象」（handle），两者并列。需确认：
   - rpa_core 是否引入 `resourceType` 字段区分 `webPage` / `windowHandle`
   - 还是用同一 `sessionId` + 扩展 `resourceType` 标签
