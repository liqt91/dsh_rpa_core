# computer use 与 RPA 的结合策略

调研日期 2026-09-22。回答两个问题：**两者怎么结合**、**RPA 是否会失去竞争力**。

前置文档：`cua-fit-assessment.md`（cua 的能力面与差距清单，§7.1 七层能力栈）、
`element-self-healing-plan.md`（自愈形态的既有结论）。

---

## 0. 结论

1. **RPA 不会失去竞争力；"只卖点击能力的 RPA"会。** 竞争不是能力对能力，而是**价值锚点位移**。
2. **RPA 的价值锚点分三阶，AI 只吃掉了第一阶。** 第二、三阶反而**因 AI 而升值**（§2）。
3. **结合的分界线是「变化率 ÷ 调用频次」，且结合点在流程之内（按环节分），不在流程之间**（§4）。
4. **我们最该走的是"AI 在设计期、不在运行期"**，而这条路的地基我们已经有了（§5.2）。
5. **修正前一轮判断**：L6 不是"缺门"，是"缺门的说明书"——CLI 早已被定为 agent 通道（§5.1）。

## 1. 行业实况（实测，非推断）

### 1.1 头部厂商的架构口径**完全一致**

| 厂商 | 事实 | 口径 |
|---|---|---|
| **UiPath** | Screen Agent（LLM 驱动的 computer-use agent）在 OSWorld-Verified 上：2025-09 用 GPT-5 排第 2，2026-01 用 Claude Opus 4.5 排**第 1**（评测由 OSWorld research group 执行；结果为厂商发布） | "**agents think, robots do, people lead**" |
| **UiPath** | `UiPath for Coding Agents`（2026-06）：Claude Code / GitHub Copilot / Gemini CLI 通过 skills + CLI 生成、校验、部署、监控 RPA 流程（XAML） | AI **生成** RPA |
| **UiPath** | Maestro（BPMN/DMN 编排）+ Maestro Case（"每案路径不同、例外常态化"的动态流程）；950 家客户在 Maestro 上编排 **36.5 万**个流程 | agent 层与 bot 层**共存** |
| **影刀** | 官方口径"**让 Agent 做大脑，让 RPA 做手脚**"；**影刀 MCP + 影刀技能（CLI）**把 RPA 应用封装成 MCP Server，供 Claude Code / Codex / Cursor / Trae 直接调用 | AI **调用** RPA |
| **影刀** | V6.0"AI 搭建流程"（自然语言生成流程）、录屏 → AI 自动拆解 SOP、智能修复（报错给修复建议甚至一键修复） | AI **生成** + AI **修复** |

**读法**：这不是某家的产品取舍，而是**行业收敛出的同一个架构**。注意方向是**双向**的——
AI 调用 RPA（MCP）+ AI 生成 RPA（Coding Agents）。两个方向对 RPA 的意义完全不同：

- 前者（被调用）→ RPA 是**依赖项**，位置稳固
- 后者（被生成）→ RPA 的"编排界面"被替代，但**执行与契约层保留**

### 1.2 市场数据：不是萎缩，是换手

| 指标 | 数值 | 来源 |
|---|---|---|
| RPA 市场 | 2025 **$28.31B** → 2026 **$35.27B**（CAGR 24.2%） | Gartner |
| Agentic AI 工作流市场 | 2025 $10.86B，CAGR **40%** | Gartner |

| 合规时点 | **EU AI Act 2026 年 8 月全面适用** | 公开 |

**这组数字说明什么**：市场仍在增长，但**份额在重新分配**。被分掉的正是
"价值只剩执行、而执行靠人肉维持选择器"的那部分（维护即最大单项成本）。
同时"40% 的 agentic 项目会取消"提醒：**纯 agent 也不是答案**——
失败原因是成本、价值与风控，恰恰是 RPA 的强项（审计、确定性）。展开见 §1.3。

### 1.3 展开：两个 40% 是同一空缺的两侧

#### 先分清成色——这两个 40% 的证据等级不同

| 结论 | 证据等级 | 出处与口径 |
|---|---|---|
| 超 40% 的 agentic AI 项目将在 2027 年底前被取消 | **Gartner 原始预测** | 2025-06 发布，基于 **3,400+ 组织**调研；三条原因：**成本上升 / 业务价值不清 / 风险控制不足** |
| 40% 的企业 RPA 部署将在 2027 年因 agentic 竞争无法达标 | **二手转述，未见 Gartner 原文** | 见于行业博客对"Gartner 2026 分析"的转述，需谨慎引用 |

> ⚠️ 文献里还有**第三个 40%**——"到 2026 年底，40% 的企业应用会嵌入特定任务的
> AI agent"（这是**正面采用率**预测）。三者在二手文章里常被混用，引用必须区分。

#### 第一个 40%（agentic 失败）：原因里**没有"模型不够聪明"**

Gartner 列的三条——成本、价值、风控——**没有一条是模型能力问题**，换更聪明的模型修不了。
配套实况（Gartner 口径）：

- 仅 **17%** 的组织在生产部署了 agent，而 60% 计划两年内 → **采用意愿与落地能力的落差**
- 过去 12 个月**只有 1/10 的用例**进了生产，原因是**信任**
- Gartner 原话："**You cannot automate something that you don't trust.**"
- **70% 的开发者**报告与既有系统集成困难
- **架构不兼容**（agent 非确定性 vs legacy 系统确定性）被点名为**项目取消的首要原因**

最后一条最关键：**agent 与既有系统的矛盾是结构性的，不是能力性的。**

#### 第二个 40%（RPA 失效）：机制是"被静默废弃"，不是"跑不动"

RPA 的失败不发警报，它会**被悄悄关掉**（业内称 "60-day cliff"）：

> 上线后运行良好 → 输入慢慢变化（表单加字段、上游导出改格式、策略调整）→
> 没有一步报错，但**微小变化的累积让流程不再匹配现实** → 某天有人决定"还不如手动做"。

原话："**Automations don't get killed for being dumb. They get killed for being
expensive to keep alive and hard to justify.**" ——**死的不是能力，是维护成本与价值证明。**

#### 镜像：两者指向同一个空缺

| | 纯 RPA | 纯 agent |
|---|---|---|
| 具备 | 确定性 · 契约 · 审计 | 适应性 · 判断力 |
| 缺失 | **适应性 · 判断力** | **确定性 · 可审计 · 问责** |
| 主要成本 | 维护（最大单项） | 治理 + ROI 度量 + 集成 |
| 结局 | 被静默废弃 | 项目被取消（40%） |

**空缺 ＝「可审计的适应性」**。两个 40% 是这同一个空缺的两侧，所以"结合"不是折中方案，
而是**补集**——市场在 2027 前后要完成一轮筛选，筛选标准就是"能否同时给出确定性与适应性"。

#### 三条但书（对 RPA 侧保持诚实）

1. **RPA 的审计优势是"要求"，不是"默认"**。要真的实现了才算数；"声明了不生效"正是
   本项目 M28–M30 一路在收的问题。这条论证对我们是**待办清单**，不是荣誉证书。
2. **"60-day cliff" 对 RPA 同样成立**。它不分技术路线，只分**有没有人负责维护**。
   所以"用 RPA 就安全"是错判。
3. **"legacy 系统不必改造"这一条被低估了**。有分析认为 agent 成功的前提是 API-first 改造，
   但 AS/400 / SAP ECC 这类系统现实中不会为 agent 改造。**RPA（或我们）是唯一
   "不需要改造就能让 agent 操作它们"的通道**，这是它在新架构里最难被替代的位置。
   前提是：**我们的执行要可靠到可以当接口用**。

## 2. 为什么会失去竞争力：价值锚点位移

RPA 的价值锚点分三阶，AI **只吃掉了第一阶**：

| 阶 | 锚点 | AI 出现前 | AI 出现后 | 变化 |
|---|---|---|---|---|
| 1 | **能操作系统**（替代人手点击） | 稀缺 → 有溢价 | agent 也会点 | **归零** |
| 2 | **可靠地操作系统**（确定性、幂等、可回放、可审计） | 附加价值 | agent 恰恰不稳 | **升值** |
| 3 | **在真实已登录环境里可靠地操作系统** | 附加价值 | 沙箱进不去已登录业务系统 | **升值** |

**"会失去竞争力"的死亡特征**（三条，命中两条即危险；这三条是判断，非实测）：

1. 主要成本落在**维护**上（维护是自动化项目的最大单项成本，口径 60%~75%，见 §1.2）
2. 不能被程序调用——无法被接进新架构（只能人开着它点）
3. 执行结果不可审计——合规场景进不去

**对照我们**：三条都不命中——成本在契约治理与流程语义（§7.1 的 L5）、
有完整 CLI 通道（§5.1）、有 `effect` / `checkpoint` / `result.json` 审计面。

> 一句话：**竞争力从"我会点界面"转移到"我能被信赖地调用"。**
> 后者要求确定性、契约、审计、真实环境——这四件恰好是 RPA 的核心资产，而不是它的负债。

## 3. 如何结合：四种形态

### 3.1 形态总表

| 形态 | 方向 | 分工 | 我们的现状 | 优先级 |
|---|---|---|---|---|
| **A. RPA 当执行后端** | agent → RPA | agent 决策 / RPA 确定性执行 | **已有 CLI 通道**（ADR 0006 §6），缺接口描述层（§5.1） | **P0** |
| **B. CUA 当异常兜底** | RPA → CUA → RPA | RPA 走主路径 / CUA 处理没见过的界面 | **缺交接契约**（§3.3） | P1 |
| **C. AI 在设计期** | AI → 草稿 AST → 运行期零 AI | AI 生成 / compiler 与人工把关 | **地基已全**（`validate` + 元素资产 + 自愈候选） | **P0** |
| **D. CUA 当流程发现者** | CUA 跑一遍 → 编译成确定性流程 | CUA 探索 / 人确认 | 缺（无录制/轨迹采集） | P2 |

> 四种形态**不互斥**，是同一架构的不同接口。行业收敛的形状是：
> **agent 层（判断）+ RPA 层（编排与确定性）+ 执行层**，CUA 从旁路接入。

### 3.2 形态 A：RPA 当执行后端（agent 调用我们）

行业已给出两条路（影刀同时用了）：**MCP**（标准协议）与 **CLI 技能**（把 CLI 操作包成
agent 的 skill）。

被 agent 调用时新增的硬约束（来自 `cua-fit-assessment.md` §3.4 的 L3 缺口）：

- **默认必须是 background 语义**。人被抢前台只是烦，agent 每调一次抢一次前台是**功能性破坏**。
- **失败必须结构化**。agent 需要可判读的原因与归因，而不是异常栈。
- **会话必须隔离**。agent 的会话不能与人的会话互踩（对应 cua 的 `start_session` 模型）。
  → 这一条我们有天然基础：浏览器侧已要求 `launch` 后显式带 session id（规则 4）。

### 3.3 形态 B：CUA 当异常兜底

RPA 跑主流程，遇到"不认识的界面 / 未覆盖的分支"→ 升级给 CUA → 处理完交回。

**这里最贵的是交接契约，不是 CUA 本身。** 要定义四件事：

1. **触发条件**：哪些失败该升级、哪些该直接失败（承接 M28"失败不盲重试"）
2. **状态移交**：当前会话/窗口/变量怎么交给 CUA——它**不能拿着我们的 session 乱点**
3. **回填与验证**：CUA 说做完了，**谁来验证？→ 必须是我们自己的确定性谓词**，
   不能采信 CUA 的自述
4. **不可回滚的边界**：涉及资金/删除/不可逆写操作的动作，不允许 CUA 自行执行

第 3 条是硬约束，与既有原则同源：**CUA 的输出是"提议"，不是"事实"**
（对照 `cua-fit-assessment.md` §4.6「模型可以提谓词，不能当裁判」）。

### 3.4 形态 C：AI 在设计期（我们最该走的路）

```text
自然语言 / 录制  →  流程草稿 AST  →  compiler 静态校验  →  人工审阅  →  运行期零 AI
```

为什么这条最适合我们：

- 保住规则 6（运行期无动态执行、无在线源码编辑）
- 保住可审计——跑的还是 AST，执行证据与今天完全一致
- **成本结构最优**：LLM 调用一次，流程跑一万次（§4）
- **地基已全**（§5.2）
- 有现成安全模板：CUA-S1 的「默认 dry run + execute/submit 两个独立 opt-in」

### 3.5 形态 D：CUA 当流程发现者

让 CUA 在目标系统里跑一遍（或人录屏 → AI 拆解），把轨迹**编译**成确定性流程。
价值：把"流程发现"这个纯人力环节自动化——影刀 V6.0 的"需求录制 + AI 拆解 SOP"就是这个。

**关键性质：CUA 只参与一次（发现），之后全走确定性——非确定性被一次性消费掉。**
我们的缺口：没有录制/轨迹采集能力。

## 4. 判据：什么时候用确定性，什么时候用 agent

不是"流程之间"分，而是**流程之内按环节分**。同一张报销流程里，
"填表录入"该确定性、"这张发票是否异常"该 agent。

```text
确定性路径  成本 ≈ 编排成本 / N  +  维护成本 × 变化频率
agent 路径  成本 ≈ 单次 LLM 成本 × N

N = 调用频次
当「变化周期」远大于「运行周期」 → 确定性胜（编译一次，跑一万次）
当「变化周期」接近或小于「运行周期」 → agent 胜（每次都重新理解）
```

实践判据（三条同时看）：

1. **变化率**：这个界面/流程多久变一次？低 → 确定性
2. **频次**：一天跑几次？高 → 确定性
3. **可判定性**：结果能否由确定性谓词验证？能 → 确定性

三条都指向确定性 → **一定用确定性**（这是经济性，不是保守）。
两条指向 agent → 才上 agent，且必须配 dry run + 人工 opt-in。

**反模式（三条，均有实证来源）**：

1. **把稳定的高频流程改用 agent** —— 单次成本 × 日频次会超过它省下的全部人力
2. **把 agent 放在无法验证的环节** —— 无法判定对错，错误静默累积（EU AI Act 下还过不了合规）
3. **没有编排层就让 agent 和 bot 各跑一套** —— 两套自动化互相踩，Forrester 称之为
   "重复 RPA 的错误"（对应 RPA 时代的 bot sprawl）

## 5. 我们的现状（实测，含对前一轮判断的修正）

### 5.1 修正一：L6 不是"缺门"，是"缺门的说明书"

前一轮（`cua-fit-assessment.md` §7.1 L6）记为"**无 agent 协议面 / 盲区**"。
**这个判断偏重了**，实测证据：

```text
src/rpa_core/cli.py:636  顶层子命令 15 个：
  validate  run  resume  pause  runs(list|show)          ← 编译校验 + 运行 + 运行控制 + 历史
  catalog                                                ← catalog 摘要
  capture(browser|desktop)                               ← 交互捕获
  elements(list|show|verify)                             ← 元素资产读写 + 验证
  auth  unauth  status  env-status  install-extension    ← 环境与安装
  gui  devserver                                         ← 两个宿主形态
src/rpa_core/cli.py:627-631   stdout/stderr 强制 UTF-8，注释写明
  "WorkBuddy statusMatch 契约依赖可解析输出"
.harness/adr/0006-api-surface.md §6（2026-09-03 增补）
  "CLI 优先：能力层每项能力必须有 CLI 入口（agent/脚本通道，M15 WorkBuddy 主路径）"
```

即：**CLI 早就是为 agent 准备的通道，而且已经有 agent 在调它**（WorkBuddy）。
ADR 0006 §6 当初列的"CLI 无入口"缺口（catalog / capture / elements）**现已全部补齐**。

**所以真实缺口是"说明书"，不是"门"**：

| 缺失 | 含义 | 成本 |
|---|---|---|
| **接口描述层**（skill / 工具清单 / 参数说明） | agent 不知道我们有哪些命令、怎么调、什么语义 | **低**（文档 + 少量 wrapper） |
| **MCP 封装**（可选） | 标准协议接入，省掉每个宿主各自的适配 | 中（需新 ADR，ADR 0006 §3 明确排除 MCP） |

**结论修正**：P0 不是"MCP 立项"，而是**"把已有 CLI 面写成 agent 可消费的接口描述"**。
MCP 是这件事的自然延伸，按需再上。

对照影刀可以看清位置：**影刀做的是"MCP + CLI 技能"双通道，
我们 CLI 通道已在，缺的正是"技能/描述"那一层。**

### 5.2 修正二：形态 C 的地基比预想的厚

| 形态 C 需要的零件 | 我们的现状 |
|---|---|
| 静态校验闸门 | **`rpa-core validate`**（= `WorkflowCompiler.compile` 的薄封装，compiler dry-run 已有） |
| 元素资产（生成目标的依据） | **已有**（M10 捕获落盘 `<flowDir>/elements/*.json`） |
| 元素候选（自愈的数据基础） | **已有**（M28 S1 运行期消费候选，带归因证据） |
| 有界谓词验证 | **有雏形**（`elements verify`；对照 cua 的 `verify_state`） |
| dry run + opt-in 安全边界 | 缺（但形状现成，抄 CUA-S1 模板） |
| 自然语言 → AST 的生成器 | 缺（这是唯一需要新增的 AI 环节） |

即：**形态 C 只缺"生成器"和"dry run 开关"，其余已在。**

### 5.3 没变的东西：护城河在 agent 架构下升值

| 资产 | 为什么在新架构下更值钱 |
|---|---|
| 流程 AST + compiler 静态校验 | agent 会犯错，需要一层**能被静态检查**的执行描述；纯 CUA 没有这一层 |
| `effect` 契约 / checkpoint / 断点续跑 | agent 的长任务需要**可中断、可恢复**；cua 的会话模型没有断点续跑 |
| 真实已登录环境 | 沙箱进不去的业务系统，是 agent 永远够不着的地方 |
| 86 条命令 + manifest 契约 | agent 要调用必须有稳定接口——**没有契约的自动化无法被 agent 使用** |

## 6. 建议（按优先级）

| 优先级 | 动作 | 理由 |
|---|---|---|
| **P0** | **把 CLI 面写成 agent 接口描述**（命令清单 + 参数 + 语义 + 典型调用序列） | 成本低、见效快；这是"门"的说明书（§5.1） |
| **P0** | **形态 C 的 dry run + opt-in 设计**（生成 → dry run 展示 → opt-in → 执行） | 我们最该走的路线，地基已全（§5.2） |
| **P1** | **「异常升级交接契约」设计**（§3.3 的四条定义） | 定义 CUA 只能在被授权的位置工作 |
| **P1** | **执行层 background 语义**（承接 `cua-fit-assessment.md` §6 的同名 P0） | agent 调用场景下"不许前台化"从可选变必需 |
| **P2** | **MCP 封装**（需新 ADR，ADR 0006 §3 现为排除项） | 接口描述的标准化延伸，取决于宿主需求 |
| **P2** | **录制 / 轨迹采集能力**（形态 D） | 降低流程发现成本 |
| **—** | **不做**：把 CUA 塞进运行期的每一步 | 成本爆炸 + 审计崩塌（§4 反模式 1、2） |

**一句话行动**：先把"门的说明书"补上（P0），再决定"门后面接谁"（B/C/D）。

## 7. 补强地图：computer use 会在哪里补强 RPA

§3 给的是**形态**（怎么接），本节给的是**补强面地图**（接上之后，非确定性具体提升了哪一环）。
每一格的状态经 **2026-09-22 源码复核**，不是写作时点的估计。

### 7.1 主线：补强的瓶颈不在 AI 侧，在收敛侧

computer use 唯一不可替代的能力是**「在设计期无法枚举的地方做出判断」**。
把它放进生产流程，风险不是"它做错"，而是"**它做错了但没人知道**"——
确定性流程的错误是**可定位的**（有错误码、有 `blockedBy`、有往返数），
非确定性判断的错误是**无声的**。所以能不能用 CUA，取决于**收敛机制有多厚**：
能否把它的自由输出收束回确定性资产，并且收束过程可审计。

> **反直觉的推论**：我们的收敛闸门最厚（compiler 静态校验 + 19 个错误码全集 +
> 候选「命中即预检」+ 每步往返数基线），所以我们反而是**最能安全引入 CUA 的一方**。
> 补强对我们不是追赶，是放大器。

### 7.2 五处补强面（地图）

| # | 补强面 | AI 补的增量 | 我们已有（实测） | 真实缺口 |
|---|---|---|---|---|
| 1 | **定位** · 选择器重识别 | 按语义定位，生成新候选 | `_element_candidates()` 候选回退（M28 S1，`browser.py:357/436-465`） | **运行期生成**新候选 |
| 2 | **判断** · 信号归类 | 把自然语言异常映射成枚举 | 19 个错误码全集（`model/errors.py`，含 COVERED/DISABLED/NOT_VISIBLE） | **错误码 → 恢复动作**路由 |
| 3 | **运维** · 漂移巡检 | 比对语义快照，失败前发现退化 | 每步 `roundTrips` + 耗时自动落盘（`browser.py:470-489` → `orchestrator.py:939`） | **阈值与跨运行比对** |
| 4 | **设计** · 流程发现 | 轨迹 → 草稿 AST | `validate`（compiler dry-run）闸门 | **录制 / 轨迹采集** |
| 5 | **契约** · 可解释性（横切） | 记录判断依据与采纳理由 | `effect` 契约（kind/replay/idempotency）+ checkpoint | **`decision` 记录类型** |

### 7.3 展开：每处的正确形态

#### 补强面 1 · 定位：选择器失效时的重识别

- **AI 增量**：按**语义**找元素（"页面上那个写着提交的主按钮"），而不是按**地址**（DOM 路径）匹配。
- **实测状态**：候选回退**已实现且形态正确**——`_element_candidates()` 反查元素资产候选，
  `_page_call_with_fallback()` 逐条重试，契约明文"不改命令参数、不写工作流文件、不做任何猜测"。
- **真实缺口**：候选**只能来自 M10 捕获时的静态枚举**。界面大改导致存量候选全部失效时，
  仍只能报 `ELEMENT_NOT_FOUND`。运行期没有"生成新候选"的能力——这一条才是 CUA 的增量。
- **正确形态（三条）**：
  1. **新候选进候选池（待审区），不能直接成为主选择器**。主选择器是流程契约的一部分，
     运行期不许改写（对齐现有契约）。
  2. **采纳要有证据**：必须过 `elements verify` 的有界谓词（唯一 + 可见 + 可交互），
     并带上"为什么认为它是同一个元素"的归因。
  3. **一次性消费 → 固化**：生成一次 → 校验 → 固化成资产 → 下次不再问模型。
     **自愈的价值不在自愈，在固化**——否则每次都要自愈，成本不降。行业口径一致：
     *"The best systems also update their selector store automatically — so the next run
     uses the new correct selector."*
- **级联顺序**（UiPath Healing Agent 2026 与行业实践独立收敛出的同一条）：
  **启发式**（模糊属性 / 相邻文本）→ **语义**（LLM 读 DOM / 截图）→ **人工升级**。
  UiPath 原话值得记：*"not only relies on AI, but also combines heuristic-based strategies…
  intelligently evaluates both AI and non-AI recovery methods to select the best option"*。
  **纯 AI 自愈不是行业做法。**

#### 补强面 2 · 判断：非结构化信号归类

- **AI 增量**：把**落在建模维度之外**的输入（一句自然语言的错误提示、一个没见过的弹窗）
  映射到**有限集合**。传统 RPA 处理不了的不是"复杂逻辑"——复杂逻辑 if/else 能写；
  它处理不了的是"**输入维度没想到**"。
- **实测状态**：枚举**已存在**（19 个错误码），但**只被当作终态**，没被当作路由表的 key。
- **真实缺口**：**「错误码 → 恢复动作」的路由层**。这正是 §3.3 那个"异常升级交接契约"的
  真正形态——**交接契约不是一段文档，是一张有限的路由表**。
- **正确形态**：**模型在封闭集合里选择，不在开放空间里决策**。输出必须是枚举值或
  恢复动作 ID，不能是任意动作。与规则 6 同构：**模型可以提谓词/候选，不能当裁判**。
  行业实证（RPA+AI 可靠性工程）：异常先分类为「可恢复 / 不可恢复」再分别处理，
  是可规模化运维的前提。

#### 补强面 3 · 运维：静默腐化 → 漂移巡检（**最被低估的一处**）

- **AI 增量**：**在失败之前**发现语义退化。
- **原理性盲区**：RPA 的失败是静默的（§1.3 的 60-day cliff），因为"**每次都对，
  只是对的是旧世界**"。极端情形是**选择器还能点中（DOM 路径没变），只有语义变了**——
  一个"提交"按钮改叫"确认"，**确定性方法原理上检测不到**（它只知道匹配成功）。
  这是纯确定性手段的盲区，也是 AI 真正不可替代的地方之一。
- **实测状态**：**基线已经在了，而且是自动的**。`browser.py:470-489` 每步统计
  `round_trips`（attempts + probes）+ 耗时，经 `extension_exec.py:108-113 as_diagnostics()`
  落进 `scopes.steps.<node>.diagnostics` 与 checkpoint（`orchestrator.py:939`）。
  源码注释原话："将来任何改动让某条命令的往返数悄悄上升…都能从运行证据里直接看出来"。
- **真实缺口**：**从"有基线"到"用基线"**——没有阈值、没有跨运行比对、没有告警。
- **落地顺序（关键）**：**第一步不需要 AI**。确定性的部分（往返数异常、耗时异常、
  错误码分布变化）先做巡检；AI 只用在"语义漂移"那一半。
- **价值**：直接打在最大成本项（维护）上，把维护从**事后救火**变成**事前巡检**。
  行业实证：某保险集团靠"行为基线 + 分级告警"把场景从 80 撑到 600+、累计 3.6 万小时。
- **正确形态**：**产出「漂移报告」而不是自动修改流程**——发现漂移 ≠ 有权改流程。

#### 补强面 4 · 设计：流程发现

- **AI 增量**：真正贵的不是写步骤，是**发现该有哪些步骤**（人做流程发现要开一堆会）。
- **关键性质**：**非确定性被一次性消费掉**——CUA 只参与"发现"这一次，之后全走确定性。
- **正确形态**：**轨迹是原料不是成品**，必须过 compiler（`validate`）。这正是形态 D/C
  不失控的原因。
- **实测状态**：`validate` 闸门已有；缺录制 / 轨迹采集。

#### 补强面 5 · 契约：从"可回放"到"可解释"（横切全部）

- **AI 增量**：审计要求变了——不只是"做了什么"，还要"**为什么这么做**"。
- **关键约束**：模型的判断**不可复现**（temperature / 模型版本 / prompt 都会变），
  所以不能靠"重跑一遍"来审计。必须把判断落成**证据 + 决策记录**，
  让**决策边界可复现**（同一输入 + 同一校验规则 → 同一结果）。
- **实测状态**：`effect` 契约（kind / replay / idempotency）+ checkpoint 形状
  **完全同构**，只需加一个 `decision` 记录类型（候选来源 / 校验结论 / 采纳理由）。
- **定位**：这不是合规附加项，是**补强能不能成立的前提**——没有决策留痕，
  非确定性的错误永远无法归因，补强会净变坏。合规时点：EU AI Act 2026-08 全面适用。

### 7.4 一条边界：什么情况下"补强"是负收益

**引入 CUA 会把"选择器维护"换成"模型行为维护"，后者更难：**

| | 选择器失效 | 模型行为漂移 |
|---|---|---|
| 可定位性 | 高：有错误码、`blockedBy`、往返数 | 低：除非有决策留痕 |
| 复现性 | 高：同一环境必现 | 低：换模型/换 prompt 即变 |

所以正确的判据是：**补强是否减少了长期维护总量**。若只是把脆弱性从选择器挪到
提示词 / 模型版本，那是**负收益**——换了个地方付维护费，还失去了可定位性。

三条应用纪律（承接 §4 反模式）：

1. **稳定高频环节不动**：确定性的成本是"一次编译 + 维护 × 变化频率"，
   换成 agent 是"单次模型成本 × N"。
2. **不可验证的环节不上**：没有确定性谓词能判定对错的环节，agent 的错误会静默累积。
3. **补强点在流程之内按环节落，不在流程之间**：否则两套自动化互踩，
   就是 Forrester 说的"重复 RPA 的错误"（bot sprawl）。

### 7.5 与 §6 合并后的优先级

| 优先级 | 动作 | 为什么排这里 |
|---|---|---|
| **P0** | **用基线**：跨运行比对 `diagnostics`，产出漂移报告 | 零 AI 成本，机制已落盘，只差阈值与比对（面 3） |
| **P0** | **错误码 → 恢复动作路由表** | 形态 B 交接契约真正的样子；枚举已在，只是没当 key 用（面 2） |
| **P1** | **候选池 + `elements verify` 采纳** | 让运行期能生成新候选，但只进待审区（面 1） |
| **P1** | **`decision` 记录类型** | 其余补强的前置条件：没有它，非确定性错误无法归因（面 5） |
| **P2** | **录制 / 轨迹采集** | 面 4 的入口，价值确定但成本最高 |
| **—** | **不做**：把 CUA 放上运行期主路径 | 成本爆炸 + 审计崩塌（§4 反模式 1、2） |

> **§6 与本节的关系**：§6 的 "接口描述层 + dry run" 是**接入动作**（把门打开），
> 本节的 P0 两项是**补强动作**（让门后面的东西真的变强）。两者不冲突，可并行。
